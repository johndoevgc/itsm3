1. System Overview

VGC-ITSM is a full-stack ITIL-aligned service management platform with AI-powered automation, real-time WebSocket communication, and multi-channel integrations. The system handles incident, problem, change, request, asset, and release management with enterprise compliance capabilities.

2. Architecture Layers

2.1 Presentation Layer (Frontend)

  • Single-page React application built with Vite
  • 13 primary modules in left sidebar navigation (grouped: Core, Monitoring, AI & System)
  • End-user portal: restricted to Self-Service, Knowledge Portal, Service Catalog
  • PWA-enabled with offline manifest (/pwa/manifest)
  • Theme engine with customizable layouts and keyboard shortcuts

2.2 API Layer (Backend)

  • Raw Node.js HTTP server — no Express/Koa dependency
  • URL-based routing with method checks (GET/POST/PUT/DELETE/PATCH)
  • JWT-style session management with Entra ID token validation
  • Rate limiting: 100 req/min per user, 200 req/min per IP
  • CORS configuration for cross-origin requests

2.3 Data Layer

The database uses a document-store pattern on MySQL:

TablePurposeSchema
itsm_dataAll domain dataid (UUID), collection (varchar), data (JSON), created_at, updated_at
audit_logCompliance audit trailid, action, collection, record_id, user, details (JSON), timestamp

74 logical collections stored in itsm_data — each row is a JSON document keyed by collection + UUID. New in v3.20: pdpa_config, dsar_requests, billing_entries, sg_holidays, portal_sessions, ai_usage, ai_audit_log.

4.2 Multi-Tenant Architecture (v3.20)

  • Each customer deploys with their own M365 tenant — ALLOWED_TENANT_IDS env var restricts access
  • AUTHORITY_MODE=multi enables multi-tenant Entra authority (https://login.microsoftonline.com/common)
  • Tenant Admin role (level 0) manages per-customer users, compliance, SLA policies
  • Feature flags control module availability: FEATURE_PDPA, FEATURE_PORTAL, FEATURE_BILLING, FEATURE_SETUP_WIZARD
  • Customer provisioning via scripts/provision-customer.sh — creates DB, Entra app reg, configures DNS

5. Request Pipeline

1
HTTP request arrives at Node.js server
2
Rate limiter checks: 100 req/min per user, 200 req/min per IP
3
CORS validation and auth middleware (Entra token or local session)
4
URL routing matches endpoint → handler function
5
Cache layer checked (LRU, 5-min TTL) for read operations
6
MySQL query via document-store pattern (collection + id + JSON)
7
Response returned; audit log written for mutations
8
WebSocket broadcast for real-time UI updates

7.2 Docker Deployment

  • Multi-stage Dockerfile — build frontend with Vite, serve with Node 22 Alpine
  • .dockerignore excludes node_modules, .git, docs
  • Environment variables injected at runtime (12-factor app)
  • Graceful shutdown handler for container orchestration

7.3 Infrastructure as Code (Bicep)

  • infra/main.bicep provisions: App Service Plan, Web App, MySQL Flexible, OpenAI, Key Vault, VNet
  • Parameterized for per-customer deployment: customerName, environment, region
  • Managed Identity for service-to-service auth (no secrets in config)

7.4 CI/CD Pipeline

  • .github/workflows/deploy.yml — triggered on push to main/master
  • Stages: lint → test → build Docker image → push ACR → deploy App Service
  • Ops scripts: scripts/provision-customer.sh, scripts/update-all-customers.sh, scripts/ops-status.sh
  • Customer registry: scripts/customers.json
